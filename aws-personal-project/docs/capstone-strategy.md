# Capstone Program Strategy

## Purpose

Twelve AWS Solutions Architect capstone projects, each built from scratch as Terraform infrastructure as code, deployed to a real AWS account, tested against failure, documented with evidence, and torn down. This document is the operating standard every project follows.

---

## 1. Operating model (how every project runs)

Every project goes through the same nine steps:

| Step | What happens |
|---|---|
| 1. Design | Read the brief, write the requirements and the risks, and draw the architecture in Lucid (diagram by Adenusi) |
| 2. Plan | A short plan per project covering services, file layout, cost estimate and test plan |
| 3. Build | Terraform plus any app or Lambda code, written in the project folder |
| 4. Static checks | `terraform fmt`, `validate`, `tflint`, `checkov`, `gitleaks`, all through pre-commit |
| 5. Cost check | `infracost breakdown` on the plan before applying |
| 6. Deploy | Bootstrap the state bucket, `init`, review the `plan`, then `apply` |
| 7. Test and evidence | Run the test scripts and capture screenshots and outputs into `evidence/` |
| 8. Teardown | `terraform destroy` the main stack, keep the state bucket |
| 9. Write-up and merge | Finish the README (results, lessons learned), open a PR, merge, tag `p01-v1.0` |

**Git flow:** one branch per project (`project-01-ha-ecommerce`), conventional commit messages, one PR per project, and `main` always stays valid.

## 2. Repository standards

```
aws-personal-project/
├── README.md                     # Portfolio index: 12 projects, status, links
├── .gitignore                    # state, .terraform/, *.tfvars, backend.hcl, zips
├── .editorconfig
├── .pre-commit-config.yaml       # fmt, validate, tflint, checkov, gitleaks, terraform-docs
├── .tflint.hcl                   # aws ruleset
├── .github/workflows/terraform-ci.yml   # static checks on PRs, no AWS credentials needed
└── project-01-ha-ecommerce/      # fully self-contained
    ├── README.md                 # problem, architecture, decisions, deploy, test, results, cost, teardown
    ├── bootstrap/                # this project's own encrypted S3 state bucket and KMS key
    ├── *.tf                      # main stack, split by concern (network.tf, alb.tf, database.tf ...)
    ├── terraform.tfvars.example
    ├── backend.hcl.example
    ├── app/  scripts/  docs/  evidence/
    └── .terraform.lock.hcl       # committed, generated on first init
```

**Conventions applied to every project**
- Region `us-east-2` (plus a second region only where the brief requires one, such as Project 3 DR)
- Remote state: each project has its own S3 bucket with KMS encryption and versioning, plus S3 native locking (`use_lockfile`). No DynamoDB lock table, since that approach is deprecated
- Terraform `>= 1.11`, AWS provider `~> 6.0`, all versions pinned, lock file committed
- Naming follows `<project>-<env>-<component>`. Default tags are Project, Environment, Owner, ManagedBy=Terraform and Capstone
- No secrets in git. Passwords are generated by Terraform and stored in Secrets Manager, and RDS uses managed master passwords
- Security defaults: encryption at rest with KMS, TLS enforced, IMDSv2, private subnets for compute and data, least privilege IAM
- Repo tooling (CI, pre-commit) is shared across the repo. Infrastructure code is never shared between projects

## 4. AWS account prerequisites (Day 0, manual, about 30 minutes)

Project 5 later builds the full account and IAM baseline in Terraform. Before Project 1, though, we need a safe minimum:

1. Enable root MFA and stop using root afterwards.
2. Create one admin identity for Terraform. The preferred option is IAM Identity Center with an `AdministratorAccess` permission set, used through `aws configure sso` for short-lived credentials. The alternative is an IAM user with MFA.
3. Configure the CLI profile `aws-capstone` with default region `us-east-2`, then verify it with `aws sts get-caller-identity`.
4. Turn on IAM access to billing, set a $50 monthly budget with email alerts at 50%, 80% and 100%, and enable Cost Explorer.
5. Check the service quotas: EC2 vCPU and Elastic IPs (Project 1 needs 2 to 3 EIPs for NAT).

## 6. Cost and safety guardrails

- The budget alert is set up before Project 1 is applied.
- `infracost` runs on every plan; anything over $10 per day gets flagged before apply.
- Each environment is deployed, tested, evidence captured, then destroyed the same day. The state bucket stays (it costs pennies).
- Every resource is tagged, so Cost Explorer can be filtered by project.
- `force_destroy` is set on lab buckets so teardown never gets stuck. This is noted in each README as a lab-only setting.

---

## 7. Verification (for every project)

1. On the laptop: `pre-commit run -a` (fmt, validate, tflint, checkov, gitleaks) passes, and so does GitHub Actions CI on the PR.
2. `terraform plan` is reviewed, and the `infracost breakdown` result is within budget.
3. After `apply`, `scripts/verify.sh` checks every component and prints PASS or FAIL.
4. The project's test plan runs, with screenshots and outputs saved in `evidence/`.
5. `terraform destroy` finishes cleanly, and Cost Explorer shows no leftover spend the next day.
